## 1. 项目背景与总体架构

个人网站原本是静态网站，通过 GitHub 管理代码，并使用 Vercel 部署。

本次为 Moments（朋友圈）页面增加两个需要持久化数据的功能：

1. **点赞系统（Likes）**：访客可以为每条朋友圈点赞或取消点赞，点赞数量在不同设备间共享。
2. **匿名评论系统（Comments）**：访客无需注册账号，即可发表评论，并通过独立删除凭证修改或删除自己的评论。

由于静态网站没有自己的后端服务器，因此采用 Cloudflare Workers + D1 实现轻量级后端。

### 1.1 系统架构

```text
访客浏览器
    │
    ├── lxiang.cc
    │     │
    │     ├── moments.html
    │     ├── zh/moments.html
    │     ├── styles.css
    │     └── js/comments.js
    │
    │     JavaScript fetch()
    │
    ▼
https://api.lxiang.cc
    │
    ▼
Cloudflare Worker
名称：lx-personal-api
    │
    ├── /api/likes
    │
    └── /api/comments
    │
    ▼
Cloudflare D1
数据库：lx_personal_web
    │
    ├── 点赞数据表
    └── comments
```

### 1.2 各部分职责

| 组件 | 职责 |
|---|---|
| GitHub | 管理网站前端源代码 |
| Vercel | 部署静态网站 |
| Cloudflare Worker | 提供点赞和评论 API |
| Cloudflare D1 | 持久化点赞及评论数据 |
| 浏览器本地存储 | 保存访客标识、评论删除凭证和待恢复操作 |
| `api.lxiang.cc` | API 自定义域名 |

**重要：前端部署和后端部署是两套独立流程。**

修改 `moments.html`、`styles.css` 或 `js/comments.js`，需要通过 GitHub/Vercel 部署。

修改 Worker 代码，需要在 Cloudflare 中单独部署。

修改 D1 表结构，需要在 Cloudflare D1 Studio 执行 SQL。

## 2. Cloudflare 基础配置

### 2.1 Worker

Worker 名称：

`lx-personal-api`

API 域名：

`https://api.lxiang.cc`

目前点赞与评论共用同一个 Worker，不需要创建两个 Worker。

Worker 根据请求路径进行分发：

```text
/api/likes
    → 点赞处理逻辑

/api/comments
    → 评论列表与发表

/api/comments/:id
    → 评论修改与删除
```

### 2.2 D1 数据库

数据库名称：

`lx_personal_web`

Worker 使用 D1 Binding 访问数据库：

```javascript
env.DB
```

因此，在 Cloudflare Worker 的 Settings → Bindings 中，需要确保 D1 数据库绑定的变量名称为：

`DB`

如果绑定名称错误，Worker 将无法通过 `env.DB` 访问数据库。

### 2.3 Worker 环境变量

点赞系统使用：

`VISITOR_HASH_SECRET`

这是用于对访客 ID 进行 HMAC-SHA256 哈希的密钥。

Worker 中通过以下方式读取：

```javascript
env.VISITOR_HASH_SECRET
```

该密钥应保存在 Cloudflare Worker Secrets 中，不应写入前端 JavaScript 或公开 GitHub 仓库。

### 2.4 CORS 配置

Worker 维护允许访问的 Origin 列表，已配置过的来源包括：

```text
https://lxiang.cc
https://www.lxiang.cc
https://lixiangpage.vercel.app
https://lixiang0618.github.io
```

开发过程中还添加过一个特定的 Vercel Preview 域名。

需要注意：

- Vercel Preview 域名可能随部署变化。
- 如果预览环境出现 CORS 错误，应检查 Worker 中的 `ALLOWED_ORIGINS`。
- 不能简单地把所有 Origin 都视为可信身份。
- CORS 是浏览器跨域访问控制，不是用户身份认证。

Worker 支持的 HTTP 方法包括：

`GET, PUT, POST, PATCH, DELETE, OPTIONS`

## 3. 点赞系统设计

### 3.1 功能需求

每条朋友圈显示一个爱心按钮和点赞数量。

访客可以：

- 点击爱心进行点赞。
- 再次点击取消点赞。
- 刷新页面后保留点赞状态。
- 在中英文页面看到相同的点赞数量。

### 3.2 访客身份

点赞不需要用户登录。

浏览器为访客生成 UUID，并通过请求头传递：

```http
X-Visitor-ID: <visitor-uuid>
```

Worker 不直接将原始访客 UUID 作为数据库身份标识，而是结合服务端密钥生成 HMAC-SHA256 哈希。

基本过程：

```text
浏览器生成 Visitor UUID
          │
          ▼
请求头 X-Visitor-ID
          │
          ▼
Cloudflare Worker
          │
          ▼
HMAC-SHA256
使用 VISITOR_HASH_SECRET
          │
          ▼
数据库记录访客哈希
```

这样可以避免直接在数据库中保存原始访客 UUID。

但必须明确：这种方式只是匿名访客识别机制，不是严格的账号认证。用户清除浏览器存储或更换设备后，可能被识别为新的访客。

### 3.3 点赞 API

基础路径：

`/api/likes`

参数：

| 参数 | 作用 | 示例 |
|---|---|---|
| `type` | 内容类型 | `moment` |
| `id` | 内容唯一 ID | `moment-001` |

请求示例：

**读取点赞：**

```http
GET /api/likes?type=moment&id=moment-001
```

**添加点赞：**

```http
PUT /api/likes?type=moment&id=moment-001
X-Visitor-ID: <visitor-uuid>
```

**取消点赞：**

```http
DELETE /api/likes?type=moment&id=moment-001
X-Visitor-ID: <visitor-uuid>
```

点赞系统已通过实际请求测试，并已集成到 Moments 页面。

**注意：** 本文没有重新核对当前生产数据库中点赞表的准确名称、字段及索引。需要排查点赞 SQL 时，应以 Cloudflare D1 Studio 中的实际 Schema 为准，不要仅凭本文猜测表结构。

## 4. 匿名评论系统设计

### 4.1 功能需求

每条 Moment 拥有独立评论列表。

访客可以：

- 无需注册即可发表评论。
- 自定义昵称。
- 使用删除凭证修改昵称及正文。
- 使用相同凭证删除评论。
- 在中文和英文页面查看相同评论。
- 使用右键、长按或 `···` 菜单进行操作。

评论列表默认展示，不需要点击气泡按钮才能查看。

评论气泡按钮主要用于打开发表评论弹窗。

### 4.2 为什么使用删除凭证

评论系统没有账号体系，因此不能通过用户名或访客 UUID 可靠判断评论归属。

最终采用：

**每条评论拥有独立的随机删除凭证（Deletion Token）。**

浏览器在发表评论前生成：

- `request_id`：唯一请求 UUID。
- `deletion_token`：32 字节密码学随机数据转换成的 64 位十六进制字符串。

生成方法：

```javascript
const requestId = crypto.randomUUID();

const bytes = crypto.getRandomValues(
  new Uint8Array(32)
);

const deletionToken = Array.from(
  bytes,
  byte => byte.toString(16).padStart(2, "0")
).join("");
```

服务端只保存凭证的 SHA-256 哈希：

```text
浏览器生成 deletion_token
             │
             ▼
       POST /api/comments
             │
             ▼
        Worker SHA-256
             │
             ▼
数据库 deletion_token_hash
```

用户修改或删除评论时，需要提供原始凭证。

Worker 重新计算哈希并进行验证。

**重要：删除凭证相当于该评论的操作密码。任何获得正确凭证的人，都可能修改或删除对应评论。**

### 4.3 凭证保存机制

前端在发送 POST 之前，先保存本次请求的 UUID 和删除凭证。

原因是：网络可能出现超时，而服务器实际上已经成功写入评论。

如果请求超时后重新生成新的 `request_id`，可能造成重复评论。

正确的重试方式：

```text
首次 POST
request_id = A
deletion_token = B
        │
        ▼
网络超时
        │
        ▼
重试 POST
request_id = A
deletion_token = B
```

同一次操作必须复用原始参数。

发表成功后，前端将删除凭证与评论 ID 关联，保存在浏览器本地，并通过弹窗提供复制和备份功能。

如果用户更换设备或清除浏览器数据，需要手动输入此前保存的凭证。

## 5. D1 评论表结构

评论表名称：

`comments`

创建时采用以下结构：

```sql
CREATE TABLE IF NOT EXISTS comments (
  id TEXT PRIMARY KEY,

  content_type TEXT NOT NULL
    CHECK (content_type IN ('moment', 'blog')),

  content_id TEXT NOT NULL,

  nickname TEXT,
  body TEXT,
  deletion_token_hash TEXT,

  request_id TEXT NOT NULL UNIQUE,

  status TEXT NOT NULL DEFAULT 'visible'
    CHECK (status IN ('visible', 'hidden', 'deleted')),

  created_at TEXT NOT NULL
    DEFAULT CURRENT_TIMESTAMP,

  updated_at TEXT,
  deleted_at TEXT,

  edit_count INTEGER NOT NULL DEFAULT 0
    CHECK (edit_count >= 0),

  CHECK (
    status = 'deleted'
    OR (
      nickname IS NOT NULL
      AND length(trim(nickname)) BETWEEN 1 AND 30
      AND body IS NOT NULL
      AND length(trim(body)) BETWEEN 1 AND 500
      AND deletion_token_hash IS NOT NULL
    )
  ),

  CHECK (
    (status = 'deleted' AND deleted_at IS NOT NULL)
    OR
    (status != 'deleted' AND deleted_at IS NULL)
  )
);
```

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_comments_content
ON comments(
  content_type,
  content_id,
  status,
  created_at
);
```

```sql
CREATE INDEX IF NOT EXISTS idx_comments_created
ON comments(created_at);
```

### 5.1 关键字段说明

| 字段 | 说明 |
|---|---|
| `id` | 评论 UUID，主键 |
| `content_type` | `moment` 或 `blog` |
| `content_id` | 对应朋友圈或文章的固定 ID |
| `nickname` | 评论昵称 |
| `body` | 评论正文 |
| `deletion_token_hash` | 删除凭证的 SHA-256 哈希 |
| `request_id` | 发表评论的幂等请求 ID |
| `status` | `visible`、`hidden` 或 `deleted` |
| `created_at` | 创建时间 |
| `updated_at` | 最近修改时间 |
| `deleted_at` | 删除时间 |
| `edit_count` | 成功修改次数 |

### 5.2 数据库创建时遇到的问题

最初在 Cloudflare D1 Studio 中执行 SQL 时，出现：

```text
no such table: main.comments
```

原因是当时只执行了索引创建语句，而 `comments` 表尚未成功创建。

解决办法：

1. 先执行 `CREATE TABLE`。
2. 确认表存在。
3. 再分别执行两个 `CREATE INDEX`。

以后如果需要重建数据库，应遵循这一顺序。

## 6. 评论 API 接口规范

### 6.1 GET：读取评论

请求：

```http
GET https://api.lxiang.cc/api/comments?type=moment&id=moment-001
```

实际测试返回：

```json
{
  "success": true,
  "content_type": "moment",
  "content_id": "moment-001",
  "count": 0,
  "comments": []
}
```

GET 返回 `comments` 数组。

没有评论时返回空数组，不需要提前在数据库中注册 Moment。

评论列表只返回可见评论。

### 6.2 POST：发表评论

请求：

```http
POST https://api.lxiang.cc/api/comments
Content-Type: application/json
Origin: https://lxiang.cc
```

Body：

```json
{
  "content_type": "moment",
  "content_id": "moment-001",
  "nickname": "LX Test",
  "body": "This is a test comment.",
  "request_id": "<UUID>",
  "deletion_token": "<64位十六进制凭证>"
}
```

实际成功响应：

```json
{
  "success": true,
  "comment": {
    "id": "9a4389d3-1e50-492b-910e-650c70c7f3e1",
    "content_type": "moment",
    "content_id": "moment-001",
    "nickname": "LX Test",
    "body": "This is a test comment.",
    "created_at": "2026-10-29 16:25:49",
    "updated_at": null,
    "edit_count": 0
  },
  "request_id": "3c1028d3-a6e6-4bed-82f8-d3d9e4e93ebe"
}
```

服务器通过唯一 `request_id` 防止重复创建。

当前 Worker 使用 `INSERT OR IGNORE`，随后根据 `request_id` 查询记录，并检查相关参数及凭证哈希，以处理重复请求。

### 6.3 PATCH：修改评论

请求：

```http
PATCH /api/comments/:id
```

Body：

```json
{
  "deletion_token": "<原始凭证>",
  "operation_id": "<新UUID>",
  "nickname": "LX Test Edited",
  "body": "This comment has been edited successfully!",
  "expected_edit_count": 0
}
```

实际成功响应：

```json
{
  "success": true,
  "comment": {
    "id": "9a4389d3-1e50-492b-910e-650c70c7f3e1",
    "content_type": "moment",
    "content_id": "moment-001",
    "nickname": "LX Test Edited",
    "body": "This comment has been edited successfully!",
    "created_at": "2026-10-29 16:25:49",
    "updated_at": "2026-10-29 16:28:41",
    "edit_count": 1
  },
  "operation_id": "b2c36c4a-9627-482c-b3d0-10c52d7f6c18"
}
```

这里使用 `expected_edit_count` 实现乐观并发控制。

例如当前 `edit_count = 1`，下一次修改必须提交：

```json
{
  "expected_edit_count": 1
}
```

成功后修改次数变为 `2`。

如果版本不一致，前端应提示用户重新获取最新内容，而不是静默覆盖。

### 6.4 DELETE：软删除评论

请求：

```http
DELETE /api/comments/:id
```

Body：

```json
{
  "deletion_token": "<原始凭证>",
  "operation_id": "<新UUID>"
}
```

删除时，Worker 将评论状态设置为：

```text
status = deleted
```

同时：

```text
nickname = NULL
body = NULL
deletion_token_hash = NULL
deleted_at = 删除时间
```

但保留评论 ID、创建时间及修改次数等必要记录。

这样属于软删除，不是从数据库中直接删除整行。

## 7. DELETE 测试中发现的重要问题

这是本次开发最值得保留的一条 Debug 记录。

### 7.1 现象

调用 DELETE 时，曾收到：

```json
{
  "success": false,
  "error": "COMMENT_NOT_FOUND"
}
```

初看似乎表示评论不存在或删除失败。

但随后在 D1 Studio 中执行：

```sql
SELECT
  id,
  nickname,
  body,
  status,
  deleted_at,
  edit_count
FROM comments
WHERE id =
'9a4389d3-1e50-492b-910e-650c70c7f3e1';
```

实际结果为：

```text
status      = deleted
nickname    = NULL
body        = NULL
deleted_at  = 有时间
edit_count  = 1
```

说明评论实际上已经成功软删除。

### 7.2 原因分析

当前 Worker 在删除时会清除 `deletion_token_hash`。

已经删除的评论再次收到 DELETE 请求时，可能直接返回：

`COMMENT_NOT_FOUND`

因此：

**`COMMENT_NOT_FOUND` 不一定表示之前的删除没有成功。**

本次实际观察证实评论已被删除，但无法仅凭数据库状态确定第一次请求的响应为什么没有显示成功。

### 7.3 当前前端解决方案

如果 DELETE：

- 返回 `COMMENT_NOT_FOUND`；
- 网络超时；
- 或发生不确定的网络错误；

前端重新 GET 当前 Moment 的评论列表。

如果评论仍然可见，保留评论并显示错误提示。

如果评论已经不在公开列表中，更新界面并提示：

`评论已不可见 / Comment is no longer visible`

不能直接声称当前请求已成功完成身份验证和删除。

### 7.4 后续可优化方向

当前 DELETE 尚不具备严格的持久化操作幂等机制。

如果以后需要更强的一致性，可以增加独立的操作记录表，记录删除操作的 `operation_id`、评论 ID 和经过验证的操作结果。

但目前前端容错已足以处理基本用户体验问题，不必为了这个问题立即重构数据库。

`Sharing my daily life and thoughts`

以及：

`分享生活点滴`

并收紧 Moments / 朋友圈标题上下的留白，保持原有主标题字体大小及三栏布局。

### 8.4 时间处理

D1 返回时间示例：

`2026-10-29 16:25:49`

这种格式没有显式时区信息。

D1 的 `CURRENT_TIMESTAMP` 使用 UTC 时间，因此前端需要按 UTC 解析，再转换为浏览器所在时区。

不能直接将该字符串当作本地时间，否则可能出现 8 小时偏差。

开发中已进行 UTC+8 时间解析检查。

## 9. 新增朋友圈时如何处理 ID

**不需要手动在 D1 中新增朋友圈记录。**

当前 D1 评论表保存的是评论，不是朋友圈本身。

例如新增一条朋友圈：

`moment-003`

前端调用：

```http
GET /api/comments?type=moment&id=moment-003
```

如果还没有评论，返回空数组。

当有人发表评论时，Worker 自动将评论关联到：

```text
content_type = moment
content_id   = moment-003
```

### 必须遵守的规则

1. 每条 Moment 使用唯一且稳定的 ID。
2. 中英文对应内容使用相同 ID。
3. 新增 Moment 时不能改变旧 Moment 的 ID。
4. 不要根据列表位置重新编号已有 Moment。
5. 不要重复使用已经删除的 Moment ID。

尤其要防止一种问题：

如果旧朋友圈 ID 是按照 DOM 顺序自动生成的，那么在顶部插入新朋友圈可能导致原有评论错位。

以后新增内容前，最好让 Codex 检查现有 ID 是否固定。

## 11. 常见故障排查指南

### 11.1 点赞或评论全部无法加载

先检查：

```text
https://api.lxiang.cc
```

以及：

```text
https://api.lxiang.cc/api/comments?type=moment&id=moment-001
```

然后打开浏览器开发者工具：

`F12 → Network`

重点检查：

- 请求是否真正发出。
- HTTP 状态码。
- Response Body。
- 是否出现 CORS 错误。
- 请求 URL 是否正确。
- Worker 是否已经部署最新代码。
- D1 Binding 是否仍然为 `DB`。

### 11.2 预览网站出现 CORS 错误

可能原因：

Vercel Preview 域名不在 Worker 的 `ALLOWED_ORIGINS` 中。

解决：

检查当前 Preview 的完整 Origin，并与 Worker 配置比较。

不要直接修改前端 API 地址来绕过问题。

### 11.3 出现 `no such table: comments`

检查：

1. Worker 是否绑定正确的 D1 数据库。
2. D1 Studio 中是否存在 `comments` 表。
3. 是否误用了其他数据库或环境。
4. 表创建 SQL 是否成功执行。

### 11.4 评论发表后出现重复内容

检查：

- POST 超时后是否生成了新的 `request_id`。
- 前端是否重复绑定事件。
- 发送期间是否禁用了提交按钮。
- 重试时是否复用了原始请求参数。
- D1 中 `request_id` 的 UNIQUE 约束是否存在。

### 11.5 修改评论失败

检查：

- 评论 ID 是否正确。
- 删除凭证是否正确。
- 评论是否仍然处于 `visible` 状态。
- `expected_edit_count` 是否等于数据库当前值。
- 是否发生并发修改。

不要通过关闭版本检查来掩盖编辑冲突。

### 11.6 删除返回 `COMMENT_NOT_FOUND`

先执行：

```sql
SELECT
  id,
  status,
  deleted_at
FROM comments
WHERE id = '<comment-id>';
```

如果 `status = deleted`，说明该评论已经软删除。

如果 `status = visible`，则继续检查请求 URL、评论 ID 和 Worker 逻辑。

如果没有记录，检查数据库环境或是否发生物理删除。

### 11.7 评论时间差 8 小时

检查前端是否将 D1 UTC 时间错误地解释为浏览器本地时间。

重点查看：

`js/comments.js`

中的日期解析与相对时间格式化函数。

### 11.8 中英文页面评论不一致

首先比较两边 Moment 的 `content_id`。

如果不同，就会请求两组不同的评论数据。

不需要修改数据库，只需修复前端 ID 映射；但如果已经有评论写入错误 ID，则需要另行评估数据迁移，不能随意覆盖。

### 11.9 新增朋友圈后旧评论错位

高度怀疑 Moment ID 根据页面顺序自动生成。

检查是否存在类似：

```javascript
const id = `moment-${index + 1}`;
```

这种逻辑。

应改为稳定、明确的内容 ID，并谨慎处理已有评论的关联关系。

### 11.10 评论样式异常但 API 正常

优先检查：

- `styles.css` 是否加载最新版本。
- 浏览器缓存。
- CSS 选择器是否冲突。
- 中英文页面是否引用相同资源。
- 手机端媒体查询是否覆盖桌面样式。
- `js/comments.js` 是否成功加载。

这类问题一般不需要修改 Worker 或 D1。

## 12. 常用 SQL 调试语句

### 查询最新 20 条评论

```sql
SELECT
  id,
  content_type,
  content_id,
  nickname,
  status,
  created_at,
  updated_at,
  edit_count
FROM comments
ORDER BY created_at DESC
LIMIT 20;
```

### 查询某条朋友圈的全部评论

```sql
SELECT *
FROM comments
WHERE content_type = 'moment'
  AND content_id = 'moment-001'
ORDER BY created_at;
```

### 查询所有已删除评论

```sql
SELECT
  id,
  content_id,
  created_at,
  deleted_at,
  edit_count
FROM comments
WHERE status = 'deleted'
ORDER BY deleted_at DESC;
```

### 统计每条朋友圈的可见评论数量

```sql
SELECT
  content_id,
  COUNT(*) AS comment_count
FROM comments
WHERE content_type = 'moment'
  AND status = 'visible'
GROUP BY content_id
ORDER BY comment_count DESC;
```

### 检查重复 request_id

```sql
SELECT
  request_id,
  COUNT(*) AS n
FROM comments
GROUP BY request_id
HAVING COUNT(*) > 1;
```

正常情况下，由于 UNIQUE 约束，不应存在重复的 `request_id`。

## 13. 安全限制与未来优化

目前系统适合个人网站的轻量级匿名互动，但并不等同于完整的商业评论平台。

### 已实现的保护

- 评论删除凭证使用密码学安全随机数生成。
- 服务端只保存删除凭证哈希。
- 修改和删除需要凭证验证。
- 输入长度限制。
- 评论正文按纯文本渲染，避免 HTML 注入。
- `request_id` 防止重复创建。
- `expected_edit_count` 防止静默覆盖。
- CORS 限制跨域访问来源。
- 删除使用软删除机制。

### 尚需考虑的功能

**1. 防刷和限流**

目前尚未确认已经部署完整的服务端限流机制。

如果以后出现机器人刷评论，可以考虑：

- Cloudflare Turnstile。
- Cloudflare Rate Limiting。
- 按 IP 或其他风险信号进行适度限制。
- 评论发送频率限制。

需要注意隐私、误封和正常访客的使用体验。

**2. 评论审核**

数据库已经预留：

`status = hidden`

未来可以实现管理员隐藏违规评论的功能。

但目前没有完整的管理员后台。

**3. DELETE 严格幂等**

未来可使用操作记录表保存已验证的删除操作结果，改善超时重试的确定性。

**4. Blog 评论**

数据库已经支持：

`content_type = blog`

未来可以复用评论组件，只需要为每篇文章分配固定 ID，并将组件挂载到 Blog 页面。

## 14. 维护原则

后续遇到问题时，优先按照以下顺序排查：

**第一层：前端**

检查 HTML、CSS、JavaScript、浏览器 Console 和 Network。

**第二层：API**

检查 Cloudflare Worker 的路由、HTTP 状态码、请求参数、CORS 和日志。

**第三层：数据库**

检查 D1 Binding、Schema、SQL 查询和数据状态。

**第四层：部署**

检查 GitHub 分支、PR、Vercel 部署和 Worker 发布版本。

不要在没有定位问题的情况下，同时修改前端、Worker 和数据库。

每次修改应尽量只涉及一个层次，并在修改后重新运行测试。

## 15. 最重要的技术结论

1. **静态网站通过 Cloudflare Worker + D1 实现点赞与评论持久化，不需要传统后端服务器。**
2. **点赞通过访客 UUID 的 HMAC 哈希识别匿名访客；评论通过每条评论独立的删除凭证授权修改和删除。**
3. **评论通过 `content_type + content_id` 关联内容，不需要预先在数据库中创建朋友圈记录。**
4. **`request_id` 是防止重复发表评论的关键，网络重试必须复用原始请求 ID 和凭证。**
5. **`expected_edit_count` 用于编辑冲突检测。**
6. **DELETE 软删除后可能再次返回 `COMMENT_NOT_FOUND`，不能仅凭这个错误判断此前删除失败。**
7. **中英文页面必须保持相同的 Moment ID，否则评论会分离。**
8. **新增朋友圈时只需新增稳定的内容 ID，不需要修改 D1。**
9. **前端、Worker、D1 和部署是不同层次，Debug 时应分层定位。**
10. **未来扩展 Blog 评论时，优先复用现有评论模块和数据库结构，不需要重新搭建系统。**
